# ADR-0025: Deterministic first, explainable weighted scoring second, human review third

- Status: Accepted (provisional)
- Date: 2026-08-29

## Context

§49 requires a three-stage resolution process with explainable scores, a review queue,
persisted decisions, and no opaque model. §80 forbids AI/ML matching outright: "clean
deterministic data first".

## Decision

### Stage 1 — deterministic

Exact agreement on a trusted key immediately links, with no scoring:

- a manually established crosswalk (always highest authority)
- an exact trusted external identifier: DUNS, GLN, or tax identifier where present and
  marked trusted
- an existing source crosswalk (the same source record already mapped)
- exact normalized website domain **plus** a high-confidence name match
- exact normalized address **plus** a high-confidence name match

### Stage 2 — explainable weighted scoring

A transparent additive model, entirely configuration-driven, using PostgreSQL-native
similarity (`pg_trgm` for names, `fuzzystrmatch`/Double Metaphone for phonetics):

| Signal                                                                | Method                       | Weight (initial) |
| --------------------------------------------------------------------- | ---------------------------- | ---------------- |
| Normalized name similarity                                            | trigram                      | 0.30             |
| Name token containment (after removing legal suffixes and stop words) | set overlap                  | 0.10             |
| Alias match                                                           | exact on known aliases       | 0.15             |
| Address line similarity                                               | trigram on normalized line 1 | 0.15             |
| Postal code equality                                                  | exact                        | 0.10             |
| City + state equality                                                 | exact                        | 0.05             |
| Email/website domain equality                                         | exact                        | 0.10             |
| Phone equality (normalized to E.164)                                  | exact                        | 0.05             |
| Shared parent organization                                            | graph                        | 0.05             |
| Explicit negative evidence (`KNOWN_DIFFERENT`)                        | veto                         | −∞               |

Name normalization is its own tested component: case folding, accent stripping,
punctuation removal, legal-suffix normalization (`Inc`, `Incorporated`, `LLC`, `L.L.C.`,
`Co`, `Corp`, `Ltd`), and industry stop words. It is versioned, because changing it
changes every score.

**Every candidate stores its feature vector**, so the review screen shows _which signals
fired and what each contributed_ — not a bare number. That is the §49 explainability
requirement, met literally.

Thresholds: `auto_link` (default 0.92), `review` (default 0.65). Below `review`,
nothing is created. Above `auto_link`, a link is created automatically **and is still
recorded as a merge with full evidence**, so it is reversible like any other (ADR-0012).

### Stage 3 — human review

`party.match_candidate` carries status `PENDING`, `APPROVED`, `REJECTED`, `DEFERRED`,
`KNOWN_DIFFERENT`, plus decider, timestamp, and reason. A rejected pair records an
**evidence fingerprint**; it does not resurface unless the evidence materially changes,
which is what stops the queue becoming noise.

### Blocking

Full pairwise comparison is quadratic and unacceptable. Candidate pairs are generated by
blocking keys — postal code, name trigram prefix, domain, phone — and only blocked pairs
are scored. Blocking recall is itself measured against a labelled fixture set.

## Alternatives considered

- **ML / embeddings / vector similarity.** Forbidden by §80, and correctly: an
  unexplainable merge of two customer accounts is not defensible to the salesperson whose
  account disappeared.
- **A commercial MDM matching engine.** Cost and lock-in disproportionate to FSW's
  record counts.
- **Deterministic only.** Insufficient: the motivating duplicates ("Acme Pharma LLC" /
  "ACME Pharmaceutical" / "Acme Pharma - West Chester") share no trusted key.

## Consequences

- Weights and thresholds are configuration (ADR-0017) and are tuned against a labelled
  fixture set with precision/recall reported, not adjusted by intuition.
- The review queue needs an owner. Without a named steward it becomes a landfill — this
  is question B5 and gap #5, and it is a people problem the architecture cannot solve.

## Risks

Threshold miscalibration causing bad automatic merges. Mitigated by a conservative
default, by full reversibility, and by starting with `auto_link` effectively disabled
(threshold 1.01) until precision is measured on real data.

## Reversal cost

Low — matching is recomputable and merges are reversible.

## Revisit if

Precision/recall on real FSW data is unacceptable after weight tuning, which would
justify a labelled-training approach — with explainability preserved as a hard constraint.
